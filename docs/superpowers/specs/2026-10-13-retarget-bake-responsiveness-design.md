# 导入目标并重定向：烘焙不再卡住界面

日期：2026-10-13  
状态：待实现  
咨询：Codex CLI `codex exec`（只读，模型 gpt-6-astra，session `01a1334b-2b68-7883-b43e-3cc5a958ec31`）。本次没有改插件代码，也没有跑性能实测。下面的耗时排序是源码结构推断，实施时用计时确认。

## 问题

点击「导入目标并重定向」（`hr.import_target_retarget`）时，Blender 窗口长时间不能操作。用户要的是同一次点击仍然导入目标并把来源动画烤到目标上，姿势与现在一致，界面在烘焙期间能画出进度并保持可响应。

常见输入是一份带多段片段的 glTF 来源，加上一份带骨架的角色 FBX。当前角色 `body.FBX` 只有 615 个顶点，顶点权重扫描本身很轻。来源网格可能更大。真正把时间乘开的是：每个片段、每一帧、每根已映射骨骼都做一次全场景求值。

## 现状

`HR_OT_import_target.execute` 在一次调用里跑完 `load_target_and_retarget`：

1. 同步导入目标文件。FBX 或 glTF 导入是 Blender 自带操作，不能从中间切开。
2. 骨架可用就直接映射；没有可用骨架才自动绑定。自动绑定同样是同步的。
3. `bake_retarget` 烤完 `collect_actions` 返回的全部片段后才返回。

`collect_actions` 合并 `hr_actions`、当前 Action 和全部 NLA 片段。面板上的「动作」下拉只影响预览，不限制这次烘焙。一份 10 段、每段约 50 帧的 glTF 会全部烤进去。

每一帧的显式求值大约是「实际求解的骨骼数 + 5」，另外 `scene.frame_set` 自己还会求值一次：

- `frame_set` 之后一次 `view_layer.update`
- `_apply_body_orientations` 把映射骨骼清零后再更新一次
- 父骨骼优先，每写完一根骨骼再更新一次，因为下一根要读 `parent.matrix`
- 朝向写完、髋位移写完、IK 之后又各更新一次

脚和手 IK 默认关闭，`apply_contact_ik` 会立刻返回，但它后面的那次更新仍然执行。

`_apply_body_orientations` 每一帧对来源和目标各调用一次 `classify_armature`。分类会走名称匹配和几何匹配。名称匹配里的 `skinned_bone_names` 扫描绑定网格的全部顶点权重。几何匹配使用 `matrix_world`。身体坐标系本身只用 rest 的 `head_local`，不随姿势变。这些准备结果在一次烘焙里通常不变，现在却按帧重做。

每根映射骨骼每帧调用两次 `keyframe_insert`（四元数和位移）。10 段 × 50 帧 × 15 根骨骼大约是 15000 次插入。

操作带 `REGISTER` 和 `UNDO`。撤销在操作结束时记一整步，不是卡顿的主因，但结束时会有一次内存开销。

`gizmos.py` 的 `POST_VIEW` 回调在 `draw_bone_gizmos` 默认开启时读取求值后的骨架。当前卡死期间窗口通常画不出来，所以 Gizmo 不是现在这次冻结的主因。改成 modal 之后，每次让出主线程都会重绘，那时必须在烘焙期间关掉它。

## 原因排序

| 顺序 | 原因 | 为什么贵 |
|---|---|---|
| 1 | 烘焙在 `execute` 里同步跑完 | 事件循环要等全部片段结束。文件选择器的 modal 不覆盖烘焙。 |
| 2 | 每根骨骼一次依赖图更新，再乘上全部片段和全部帧 | `frame_set` 已经要求值蒙皮网格。骨骼循环里的更新把同一件事重复十几次。 |
| 3 | 一次点击烘焙全部片段 | 下拉框里选中的片段不是烘焙范围。 |
| 4 | 每帧重新分类两套骨架 | 目标只有 615 顶点时这项便宜；来源网格密、片段多时它会被乘上去。 |
| 5 | 每通道 `keyframe_insert` | RNA 查找和曲线维护。首版先不动，避免插值和行为一起变。 |
| 6 | FBX 导入和自动绑定 | 小 FBX 通常短。没有可用骨架时的自动蒙皮可能单独卡住，modal 切不开这一步。 |
| 7 | Gizmo | 改成 modal 之后才变成每拍一次的开销。 |

默认 IK 的函数本身不贵。不要为了这次优化改 IK 公式。

## 方案

| 方案 | 结果 | 代价 |
|---|---|---|
| 只把烘焙切成 modal 时间片 | 窗口能画进度 | 总时间几乎不变。一帧若超过几十毫秒，那一拍仍然顿一下。 |
| 缓存稳定数据，主线程按时间片烘焙，再逐项去掉重复求值 | 窗口可响应，总时间下降，姿势公式不动 | 必须用逐帧四元数对比证明没有变。采用这个。 |
| 另开一个 Blender 进程烘焙 | 导入和蒙皮也能离开当前窗口 | 要传递未保存场景、把 Action 导回来、还要做一次撤销。这次不做。 |

不把 `bpy` 放进 Python 工作线程。Blender 的 RNA 不是线程安全的。

## 选定设计

烘焙拆成一次准备和许多小步。测试和「重定向到当前目标」继续调用同步的 `bake_retarget`，它内部把同一步骤跑完。面板上的「导入目标并重定向」在文件导入之后改走 modal。

### 准备一次

新增 `RetargetBakeJob`，只活在这一次烘焙里。准备阶段做完这些事，帧循环不再重做：

- 解析映射，并做现有的胸部和蒙皮骨骼修正。修正规则不变。
- 按目标骨骼深度和 `_BODY_ROLE_ORDER` 排序。
- 缓存每根骨骼的 rest 朝向、父深度、链末端骨骼名。
- 缓存来源和目标的身体坐标系。坐标系仍由 `_body_matrix` 从 rest `head_local` 算出。
- 记下两个骨架对象的 `matrix_world`。某一帧之后如果对象矩阵变了，这一帧重新分类并重算身体坐标系。分类结果依赖 `matrix_world`，对象被动画推动时不能一直用第一帧的分类。
- 链末端只看骨骼层级和映射，不看姿势，不用每帧重算。
- 身高比例、参考姿势、是否原地，在准备时算好。

缓存不写入场景，不跨两次点击保留。骨架、权重或映射在烘焙中途被改掉时，这一步直接失败并取消，不使用过期缓存。

### 求解顺序不动

`_apply_body_orientations` 继续按现在的顺序做：清零映射骨骼，父骨骼优先，swing 公式、身体坐标系、链末端规则、矩阵乘法和四元数转换都不改。

第一版仍然在每根骨骼之后调用 `view_layer.update`。下一根骨骼读的是 `parent.matrix`，不能在对比通过之前删掉这次更新。

可以先从帧循环里拿掉、并且每一项都要单独对比的更新：

- `frame_set` 紧后面的那次更新。`frame_set` 已经求值。
- 朝向全部写完之后、髋位移之前的那次更新。髋位移要读的是刚写完的姿势；如果对比失败就加回来。
- IK 关闭时，IK 调用之后的那次更新。IK 打开时保留。

### 第二阶段才去掉逐骨更新

对比通过之后，用本地矩阵代替 `parent.matrix`，这样每帧只保留 `frame_set` 带来的那一次来源求值。

父骨骼的骨架空间矩阵按 Blender 的姿势公式在 Python 里递推：已写好的 `matrix_basis` 乘到 rest 上，再乘父矩阵。子骨骼读这份递推结果，不再读求值后的 `parent.matrix`。

出现下面任一情况就退回逐骨 `view_layer.update`，不做递推：

- 该姿势骨骼上有约束
- 骨骼的 `inherit_scale` 不是 `FULL`
- 对比发现四元数或位移有任何一位不同

这次不改目标的 rest，不改 swing 数学。

### 插帧

第一版继续用 `keyframe_insert`。批量写 F-Curve 会碰到插值、手柄，以及「下一帧读到刚写入的目标曲线」这些条件，不和调度改动绑在一起。若第二阶段之后总时间仍明显超过一次点击可接受的范围，再单开一项做曲线批写，并对比关键帧值、插值和手柄。

### 仍然烘焙全部片段

一次点击继续烤 `collect_actions` 的全部片段。片段命名、`use_fake_user`、Blender 5 的 Action slot、NLA 轨道、时间范围，以及目标上最终选中的第一段 Action，都保持现有规则。来源骨架在烘焙结束时仍停在最后一段，这一点也不顺手改掉。

面板下拉框只负责预览。不在这次把烘焙范围改成「只烤当前片段」。

### 界面

文件选择之后：

1. 同步导入目标。这一段无法切开。导入开始前把状态写成「正在导入目标」。
2. 建立 `RetargetBakeJob`，用 `window_manager.event_timer_add` 驱动 modal。
3. 每一拍最多工作约 16 毫秒。第一版在完整的一帧结束时让出。若计时显示单帧经常超过 50 毫秒，再把一帧拆成「清零、逐骨、髋、插帧」几个小步，顺序与现在相同。
4. 状态行显示「动作 3/10，帧 21/50」。刷新不超过每秒 4 次。窗口进度条用 `progress_begin` / `progress_update` / `progress_end`。
5. 烘焙期间 `draw_callback` 在读求值骨架之前直接返回。结束后恢复用户原来的 Gizmo 开关。
6. 烘焙期间拒绝再点导入、重定向、自动绑定和会改映射的操作。Esc 取消。

「重定向到当前目标」和「给选中网格重定向」走同一个 Job。前者没有文件导入，modal 从准备阶段开始。测试路径不注册计时器。

### 取消和失败

`CANCELLED` 不会自动撤回已经写入的数据。取消或异常时 Job 自己清理：

- 删除这次新建的目标 Action
- 恢复来源原来的 Action 和 slot
- 恢复场景帧
- 若这次点击新建了目标对象，删除这次导入的对象
- 停掉计时器，结束进度条，恢复 Gizmo

成功时整次操作仍是用户的一步撤销。不逐帧压撤销，也不关掉全局撤销来提速。

插件注销时如果还有未完成的 Job，按取消路径清理。

## 不变式

下面这些结果必须和改动前逐值相同：

- 每个片段、每一帧、每根映射骨骼的 `rotation_quaternion` 和 `location`
- 四元数按 float32 的原始位比较。`q` 和 `-q` 不算相同
- 目标骨骼的 rest 矩阵
- Action 名称、slot、NLA、场景帧范围
- REST / CURRENT、保留根运动 / 原地、IK 关和 IK 开

现有测试里的方向点积只能证明肢体指向，不能证明扭转分量没变。点积测试继续留着，另外加逐值比较。

## 测试

1. 用当前代码把合成双片段骨架的烘焙结果记成基准：每根映射骨骼在每个采样帧上的四元数和位移。
2. 比较器要能认出一个分量被改掉，也要能认出取反的四元数。
3. 先只加缓存，跑比较器，必须逐位一致。
4. 再逐项删掉候选的重复 `view_layer.update`。哪一项失败就恢复哪一项。
5. 递推父矩阵单独对比。失败则只在有约束或非 `FULL` 缩放继承时走旧路径；若普通骨骼也失败，递推不进入默认路径。
6. 现有 `tests/run_retarget_test.py` 必须打印 `RETARGET_TEST_OK`。
7. 在 Blender 界面里对当前这套来源 glTF 和 `body.FBX` 点一次按钮：能看到进度，Esc 能取消并且场景回到点击前，成功之后 Ctrl+Z 撤掉整次导入和烘焙。后台测试不能代替这一步。

验收门槛是逐位一致，加上烘焙阶段窗口会让出主线程。总秒数以实施时的计时为准，不在设计里写一个没有测过的秒数。

## 非目标

- 不改 swing、身体坐标系、链末端、父优先顺序和蒙皮骨骼选择。
- 不改目标 rest。
- 不把烘焙改成只烤下拉框里的当前片段。
- 不把 FBX 导入或自动绑定搬到另一个进程。
- 第一版不批量写 F-Curve。
- 不修第 20 帧上臂朝向那件事。那是姿势定义，不是这次的卡顿。

## 自检

- 没有未定的实现步骤。父矩阵递推有明确的退回条件。
- 全部片段仍然烘焙，和「只烤当前片段」没有混在一起。
- modal 只包住烘焙。导入和自动绑定仍是同步的，文档里写明了这个边界。
- 缓存失效写的是对象 `matrix_world` 变化，不是假定它永远不变。
